# Контракт сервера

Клиент написан целиком против этого документа. Сервера ещё нет, и это ничего
не блокирует: `KcalServerSource` при пустом базовом URL просто пропускается, цепочка
идёт дальше в Open Food Facts. Когда адрес появится в `AppContainer.SERVER_BASE_URL`,
клиент менять не придётся.

Документ описывает три эндпоинта и — что важнее — два правила, которые дороже
всего чинить задним числом: разделение данных по лицензиям и порог согласия.

## Единицы

Одни и те же во всех направлениях и совпадают с доменной моделью клиента
(`n7.kcalai.model.Nutriments`). Ошибка здесь тихая и портит всё, поэтому явно:

| Поле | Единица | Пример |
|---|---|---|
| `kcal100` | целые килокалории на 100 г | `539` |
| `prot100`, `fat100`, `carb100` | **сотые грамма** на 100 г | `628` = 6,28 г |
| `servingG` | целые граммы | `15` |
| `createdAt` | миллисекунды Unix, UTC | `1757721600000` |

Сотые грамма, а не граммы с плавающей точкой, — потому что на этикетках всё равно
не больше одного знака после запятой, а фиксированная точка не копит ошибку
при пересчёте порций.

## `GET /v1/products/{gtin}`

`{gtin}` — нормализованный EAN-13 (UPC-A клиент дополняет ведущим нулём, UPC-E
разворачивает до UPC-A). Контрольная цифра проверена на клиенте, но проверьте и вы.

```
200 {
      "gtin": "4600699500001",
      "name": "Молоко 3,2%",
      "brand": "Домик в деревне",     // необязательно
      "kcal100": 59,
      "prot100": 290,
      "fat100": 320,
      "carb100": 470,
      "servingG": 250                 // необязательно
    }

404  товара нет
```

404 — штатный ответ, а не ошибка: клиент идёт дальше в OFF и, если и там пусто,
показывает человеку форму. Никакого тела у 404 не требуется.

Ответ отсюда клиент помечает `ProductOrigin.SERVER` и кладёт в `cached_product`.

## `POST /v1/contributions`

Тело — массив. Очередь копится офлайн и уходит пачкой, когда появляется сеть.

```json
[
  {
    "gtin": "4600699500001",
    "name": "Молоко 3,2%",
    "kcal100": 59,
    "prot100": 290,
    "fat100": 320,
    "carb100": 470,
    "servingG": 250,
    "createdAt": 1757721600000
  }
]
```

```
202 { "accepted": ["4600699500001"] }
```

`accepted` — те GTIN, которые приняты в обработку. Клиент помечает `sentAt` только
у них; остальные остаются в очереди и уедут снова. Повторная присылка того же GTIN
штатна и должна быть идемпотентной по смыслу: это ещё один голос, а не дубликат.

**Идентификатора пользователя в теле нет и не будет.** Что человек ест — медицинские
данные, и отсутствие аккаунта в v1 стоит сохранить. Если для защиты от накрутки
понадобится различать источники, это должен быть непривязываемый к человеку токен
устройства, а не учётная запись.

## `GET /v1/slice/manifest.json`

Срез для докачки на клиент (План 4, здесь только ради полноты контракта).

```json
{
  "version": 7,
  "url": "https://.../slice-7.db.zst",
  "sha256": "…",
  "sizeCompressed": 18400000,
  "rowCount": 240000
}
```

## Порог согласия

Один человек с опечаткой не должен править цифры для всех.

Значение по GTIN публикуется, когда **N независимых вкладов сошлись** — совпали
в пределах того же допуска, с которым клиент сверяет энергобаланс (25%). До этого
GTIN отдаётся как 404: лучше отправить человека в форму, чем показать ему чужую
опечатку. Разумный старт — N = 3, с понижением до 2 для категорий, где вкладов мало.

Без порога первая же опечатка разъезжается по всем пользователям, и откатить её
некому: обратной связи «это неверно» в клиенте нет.

Дополнительно на входе стоит повторить проверки `NutrimentValidator`: ккал
в 0..900, макросы в 0..100 г, сумма макросов не больше 100 г. Клиент их уже сделал,
но клиент — не то место, на которое сервер вправе полагаться.

## ODbL: чего серверу делать нельзя

Open Food Facts лежит под ODbL — лицензией с share-alike на **производную базу**.
Если данные из OFF попадут в общий пул и будут из него раздаваться, публиковать
придётся весь пул целиком, включая вклад ваших пользователей.

Клиент это разделение уже гарантирует конструкцией: ответы OFF живут в отдельной
таблице `cached_product` с пометкой `ProductOrigin.OFF`, а очередь отправки
собирается из `user_food`, куда сеть не пишет никогда. Физически заразить пул
клиент не может.

Симметричное правило для сервера:

- в пул принимается только то, что пришло через `POST /v1/contributions`;
- импортировать дамп OFF в тот же пул нельзя — ни разово, ни «только для России»;
- если понадобится отдавать данные OFF через свой API, они должны жить в отдельном
  хранилище, отдаваться с пометкой источника и не смешиваться с вкладами.

## Веб-поиск как серверная обязанность

Российское покрытие OFF — порядка тридцати шести тысяч товаров, и промах остаётся
основным исходом скана. Нарастить покрытие можно поиском по вебу: карточки
маркетплейсов и сетей обычно содержат таблицу КБЖУ, и GTIN по ним находится.

Это работа сервера, а не клиента, по трём причинам: нужен платный search API,
а ключ в APK не положишь; парсинг чужих карточек хрупок и требует починки без
релиза приложения; и человек у полки не будет ждать несколько секунд.

Естественное место — обработчик неизвестного GTIN: отдать 404 сразу, а в фоне
поставить задачу «поискать», чтобы к следующему запросу ответ уже был в пуле.
Клиент при этом не меняется вообще.

Юридически это единственный чистый путь роста: найденное веб-поиском не производно
от OFF, share-alike на него не распространяется, и в общий пул оно ложится законно.
Найденное таким образом стоит проводить через тот же порог согласия — источник
в вебе тоже бывает неправ.
