# builddb

Сборка справочной базы Kcal AI.

`build_seed.py` собирает `out/seed.db` из CSV в `data/` и копирует результат
в `app/src/main/assets/`. Только стандартная библиотека Python — ставить нечего.

## Запуск

```bash
python3 build_seed.py            # собрать и проверить инварианты
python3 build_seed.py --install  # то же + положить в app/src/main/assets/ и server/data/seed/

python3 merge_generated.py items.json --dry-run  # посмотреть, что примется
python3 merge_generated.py items.json            # влить новые позиции в CSV
```

Ненулевой код возврата означает, что сборка нашла нарушенный инвариант и база
в assets НЕ обновлена.

`--install` кладёт рядом с базой `seed.db.sha256`. По нему приложение понимает,
что справочник сменился. Отличать версии по размеру файла нельзя: SQLite выравнивает
базу по страницам, и правка текста внутри строки его не двигает.

`merge_generated.py` вливает сгенерированные позиции и сам отбраковывает мусор:
занятые id и ключи, числа вне диапазонов, расхождение ккал с макросами больше 25%,
единицы вне канона. Алиас, уже занятый другой позицией, отбрасывается — существующие
данные курировались дольше, и поведение поиска на них уже завязано.

## Данные

| Файл | Кто правит | Что внутри |
|---|---|---|
| `data/generic.csv` | генерируется целиком | продукт, КБЖУ, типичная порция |
| `data/generic_alias.csv` | генерируется целиком | как продукт называют в тексте |
| `data/generic_alias_extra.csv` | **руками** | «голые» слова: хлеб, масло, рыба, каша |
| `data/portion_unit.csv` | генерируется целиком | граммовка единиц для конкретного продукта |

Два файла алиасов раздельно намеренно: пересборка машинного `generic_alias.csv`
не должна стирать курированные соответствия из `_extra`.

## Что проверяется при сборке

- висячие ссылки в `generic_alias` и `portion_unit`;
- ккал и макросы в физически возможных диапазонах;
- типичная порция в пределах 1..2000 г;
- продукт без единого алиаса — его нельзя найти поиском;
- один алиас у двух продуктов — поиск стал бы недетерминированным;
- единица вне канона парсера (`CANONICAL_UNITS`);
- расхождение ккал с макросами больше 25% — кроме алкоголя, где часть энергии
  даёт этанол и в макросы не попадает.

## Кулинарное состояние в названии — только когда оно меняет цифры

Гречка сырая 308 ккал против отварной 110 — втрое, и состояние обязано быть
и в `name_key`, и в `name_ru`: без него трекер систематически врёт.

Морковь сырая 35 против отварной 32 — 9%. Две позиции вместо одной здесь не
уточняют ответ, а заставляют выбирать между одинаковым и занимают места в шести
подсказках. Порог — те же 25%, которыми спека меряет существенность разницы (§8).

Поэтому: варианты, различающиеся меньше чем на 25%, схлопываются в одну позицию
с нейтральным именем («Морковь», «Яйцо»), а алиасы поглощённого переезжают на неё,
чтобы поиск по ним продолжал работать.

## Единицы, ровно так

- `kcal100` — целые килокалории на 100 г.
- `prot100` / `fat100` / `carb100` — **сотые грамма** на 100 г (12.34 г → `1234`).
- `grams`, `serving_g`, `default_portion_g` — целые граммы.

`REAL` не используется: фиксированная точка занимает меньше, сравнивается точно
и не зависит от десятичного разделителя в локали.

## Два места, которые обязаны совпадать

| Здесь | И там |
|---|---|
| `normalize()` | `n7.kcalai.fooddb.normalizeForSearch` |
| `CANONICAL_UNITS` | `n7.kcalai.resolver.Units` |

Расхождение не ломает сборку — оно молча портит поиск. Первое проверяется
глазами, второе — инвариантом при сборке.

## Лицензия данных

Генерик-таблица в `data/` составлена вручную. Таблицы `product_seed` остаются
пустыми до Плана 4, где в них поедут данные Open Food Facts под ODbL —
тогда же `meta` обязана получить непустые `source`, `license` и `off_dump_date`.
