# Kcal AI — дизайн

Дата: 2026-09-13
Статус: утверждён, готов к написанию плана реализации

## 1. Что строим

Android-приложение для подсчёта КБЖУ за день. Полностью работоспособно офлайн.
Три способа добавить еду: скан штрих-кода, свободный текст, ручной ввод.
Распознавание по фото — отдельный этап (v2), но архитектура закладывается сразу.

## 2. Зафиксированные решения

| Решение | Выбор | Почему |
|---|---|---|
| Аудитория | Google Play, широкая | Должно работать на бюджетнике 4 ГБ RAM без интернета |
| Срез базы | Один глобальный | Одна сборка, одно обновление, нет матрицы регионов |
| ИИ в v1 | Текст (парсер), фото позже | Работает на любом железе; фото не решает задачу порций |
| Текстовый ввод | Детерминированный парсер + FTS5, LLM опциональным фолбэком | 0 МБ, мгновенно, тестируемо |
| Доставка базы | Гибрид: ядро в APK + докачка полного среза | Полезно сразу после установки без сети |
| Структура | Многомодульно, по образцу AD2 | Сборка БД, скан и ИИ — три независимые оси изменений |

## 3. Результаты исследования (сентябрь 2026)

### Сканирование штрих-кода

`com.google.mlkit:barcode-scanning` в **bundled**-варианте: модель в APK, +~2.4 МБ,
работает без интернета и без Google Play Services.
Unbundled (`play-services-mlkit-barcode-scanning`, +200 КБ) докачивает модель — не подходит.

### Источники данных

| Источник | Товаров | Штрих-коды | Лицензия | Покрытие |
|---|---|---|---|---|
| Open Food Facts | 4.81 млн | да | ODbL | мир, перекос в Европу |
| OFF, русский раздел | 36 145 | да | ODbL | РФ/СНГ дырявое |
| USDA FDC Branded | ~368 тыс. | GTIN/UPC | public domain | США |

Полный дамп OFF — 10–43 ГБ (JSONL/CSV; Parquet на Hugging Face, обновляется ежедневно).
Нужные 7 полей дают ~60–100 байт на строку: срез «только с полным КБЖУ» ≈ 200 МБ SQLite,
~70 МБ в сжатом виде.

**Принятый риск:** значительная доля сканов не найдётся, особенно в РФ/СНГ.
Продуктовый ответ — см. раздел 8 (промах скана как основной сценарий, а не как ошибка).

### Локальный ИИ

| Путь | Умеет | Цена | Кто потянет |
|---|---|---|---|
| ML Kit GenAI (Gemini Nano) | описание фото, Prompt API | 0 МБ, модель у системы | Pixel 8+, Galaxy S24+, Pixel 10; описание фото только по-английски |
| LiteRT-LM + Gemma 3n E2B int4 | фото+текст, контекст 4096 | 3.1 ГБ, пик ~5.9 ГБ RAM | флагманы |
| Gemma 3n E4B int4 | то же, умнее | 4.4 ГБ, пик ~7.0 ГБ | топ-флагманы |

| Gemma 3 1B int4, текст | разбор фраз | ~0.7 ГБ | средний класс и выше |

**MediaPipe LLM Inference API переведён в maintenance-only.** Актуальный путь — LiteRT-LM Android (Kotlin API).

## 4. Центральный принцип

Любой способ ввода отвечает на два вопроса: **что это** и **сколько грамм**.
КБЖУ подставляется детерминированно из локальной базы. ИИ никогда не называет цифры.

```
Скан / Текст / Фото  ->  FoodResolver  ->  [ {foodRef, grams, confidence} ]
                                                  |  подтверждение человеком
                            FoodRepository.nutrimentsPer100g(foodRef)
                                                  v
                            DiaryEntry(снимок КБЖУ, граммы, время, приём пищи)
```

Следствия: способы ввода взаимозаменяемы; ИИ можно менять, докачивать и отключать
без правок UI; дневник не содержит галлюцинаций.

## 5. Модули

```
:app                    Dagger-компонент, навигация

:core:model             чистый Kotlin: Nutriments, FoodRef, Portion, MealType
:core:database          Room: дневник, свои продукты, цели, «недавнее»
:core:fooddb            read-only SQLite-срез: доставка, версии, запросы, FTS5
:core:repositories      FoodRepository / DiaryRepository поверх обеих баз
:core:designsystem      тема и компоненты Compose
:core:dagger
:core:navigator

:core:resolver:api      FoodResolver, ResolveInput, ResolvedItem
:core:resolver:impl     резолверы штрих-кода и текста

:feature:diary          день, приёмы пищи, прогресс, история
:feature:entry          свободный текст + единый экран подтверждения «что + сколько»
:feature:scanner        CameraX + ML Kit barcode (bundled)
:feature:onboarding     параметры, цели, первичная загрузка базы
:feature:settings       цели, экспорт, состояние базы, лицензии
```

Позже рядом с `:core:resolver:impl` встают `:core:resolver:llm` и `:core:resolver:vision`
отдельными модулями — их тяжёлая транзитивка не должна попадать в v1.

Контракт границы:

```kotlin
sealed interface ResolveInput {
    data class Barcode(val gtin: String) : ResolveInput
    data class FreeText(val text: String) : ResolveInput
    // v2: data class Photo(val uri: Uri) : ResolveInput
}

data class ResolvedItem(val food: FoodRef, val grams: Int, val confidence: Float)

interface FoodResolver {
    fun handles(input: ResolveInput): Boolean
    suspend fun resolve(input: ResolveInput): List<ResolvedItem>
}
```

Резолверы регистрируются через Dagger-мультибиндинг. `:feature:entry` не знает,
откуда пришёл `ResolvedItem`. Добавление фото в v2 — новый модуль и одна строка биндинга.

## 6. Модель данных

### Справочные данные — read-only, два файла с общей схемой

Схема одна, но материализуется в **два отдельных SQLite-файла**, потому что у них
разный жизненный цикл: один едет в APK и версионируется вместе с кодом, другой
докачивается и обновляется независимо.

**`seed.db` — в assets APK, 2–5 МБ:**

```sql
generic(id PK, name_key, kcal100, prot100, fat100, carb100)
generic_alias(generic_id, alias, lang)
generic_fts                    -- FTS5 по generic_alias.alias
portion_unit(generic_id, unit, grams)

product_seed(barcode PK, name, brand, kcal100, prot100, fat100, carb100, serving_g, popularity)
product_seed_fts               -- FTS5 по name + brand
```

`generic*` и `portion_unit` — генерик-таблица на 1–3 тыс. позиций, ~300 КБ.
`product_seed` — топ штрих-кодов по популярности, остальные 2–5 МБ.

**`food.db` — докачивается, ~200 МБ:**

```sql
product(barcode PK, name, brand, kcal100, prot100, fat100, carb100, serving_g, popularity)
product_fts                    -- FTS5 по name + brand
meta(key, value)               -- версия среза, дата дампа OFF, число строк
```

Оба файла открываются одним соединением через `ATTACH DATABASE`. Пока `food.db`
не скачан, брендовый поиск идёт по `product_seed`; после докачки — по `product`,
а `product_seed` перестаёт использоваться (удалять его из assets нельзя — он нужен
при переустановке и при сбросе данных).

Выбор таблицы делается **один раз при открытии соединения** и живёт в одном месте —
`FoodDbQueries`, который подставляет имя таблицы в запрос. Это единственная ветка
«есть полная база / нет», и она покрыта тестами в обоих состояниях.
Поиск по `generic` работает всегда и от состояния докачки не зависит.

**Единицы измерения, явно:**

- `kcal100` — целые килокалории на 100 г (`REAL` не используется).
- `prot100` / `fat100` / `carb100` — **сотые грамма** на 100 г (12.34 г -> `1234`).
- `grams`, `serving_g` — целые граммы.

Фиксированная точка вместо `REAL`: меньше места, точные сравнения,
нет проблем с десятичным разделителем в локалях.

### Room — изменяемые данные пользователя

```kotlin
@Entity DiaryEntry(
    id, dateEpochDay, meal,
    displayName, grams,                      // снимок, намеренно денормализован
    kcal100, prot100, fat100, carb100,
    source,      // BARCODE | TEXT | MANUAL | LLM | VISION
    foodRef?,    // только для «повторить»; может протухнуть, это нормально
    createdAt
)
@Entity UserFood(barcode?, name, kcal100, prot100, fat100, carb100, createdAt)
@Entity DailyGoal(fromDate, kcal, prot, fat, carb)
@Entity BodyMetric(dateEpochDay, weightGrams)
```

Три решения, которые потом дорого менять:

1. **Снимок нутриентов в записи дневника.** Обновление среза не должно переписывать историю.
2. **Граммы — каноническая единица**, порции только конверсия. Иначе сумма за день
   превращается в «2 штуки + 1.5 ложки + 200 г».
3. **День — epochDay в локальной зоне**, не UTC-instant. Иначе день съезжает при перелёте.

`DailyGoal` версионируется, а не перезаписывается: цель на дату D — это запись
с максимальным `fromDate <= D`. Иначе смена цели задним числом переписала бы
прогресс за все прошлые дни.

## 7. Сборка и доставка базы

Скрипт в репозитории (он же часть обязательств ODbL — публикуется):

1. Скачать дамп OFF (Parquet с Hugging Face).
2. DuckDB: оставить строки с barcode + именем + всеми четырьмя нутриентами;
   kJ -> ккал; выбросить мусор (kcal > 900 на 100 г, отрицательные, нули по всем четырём).
3. Дедуп по нормализованному GTIN-13; при конфликте выигрывает более полная запись.
4. `popularity` берётся из поля популярности OFF (`unique_scans_n`); при его отсутствии — 0.
5. Экспорт в SQLite, построить FTS5, VACUUM, сжать zstd.
6. Тем же проходом собрать `seed.db`: генерик-таблица + top-N строк `product`
   по `popularity` (N подбирается под бюджет 2–5 МБ).
7. Артефакты: `food-<version>.db.zst` + манифест (sha256, размер, дата дампа, число строк)
   и `seed.db`, который коммитится в репозиторий и едет в assets.

Доставка:

- **В APK**: `seed.db` (2–5 МБ) — генерик-таблица плюс самые популярные штрих-коды.
  Приложение полезно сразу, без единого байта сети.
- **Докачка**: полный срез по Wi-Fi через WorkManager, возобновляемая,
  проверка sha256, распаковка в `filesDir`.
- **Обновление**: манифест на CDN -> сравнение версий -> скачивание целиком.
  Дельты — только если размер станет реальной проблемой.

### Лицензия

OFF под ODbL: share-alike распространяется на **базу**, не на код приложения.
Закрытый исходник допустим при условии:

- производный SQLite-срез публикуется под ODbL;
- скрипт сборки публикуется;
- в «О приложении» указан источник Open Food Facts и ссылка на лицензию.

Это закладывается в пайплайн сборки с первого дня, а не перед релизом.

## 8. Пайплайн ввода

### Текстовый парсер

```
"200 г гречки, 2 яйца и ложка масла"
  -> сегментация: запятая / «и» / перевод строки
  -> для сегмента: [количество][единица][название]
  -> единицы: г гр g кг мл л шт ст.л. ч.л. стакан кусок порция
  -> количество без единицы -> штучный продукт -> N * portion_unit.grams
  -> FTS5 по generic_alias + product/product_seed + UserFood + недавнему
  -> ранжирование: частота у этого пользователя -> точность совпадения
                   -> generic выше product -> popularity
  -> [ResolvedItem(food, grams, confidence)]
```

Брендовые товары участвуют в текстовом поиске наравне с генериками («активиа» должна
находиться), но при равной релевантности генерик идёт выше: на «гречка» человек почти
всегда имеет в виду крупу, а не конкретную пачку.

`confidence`: точное совпадение алиаса + явная единица = `1.0`; FTS-совпадение
с явной единицей = `0.7`; совпадение без единицы = `0.5`.
**Порог автоподстановки — `0.8`.** Ниже него строка показывается как выбор из кандидатов,
а не подставляется молча. Порог — константа в одном месте, чтобы его можно было двигать
по результатам реального использования.

**Ничего не попадает в дневник без подтверждения человеком.** Экран `:feature:entry`
показывает разобранные строки с граммами, каждую можно поправить. Это защита от ошибок
парсера и одновременно готовая площадка для результатов фото в v2.

### Промах скана — основной сценарий

```
скан -> не найден -> форма «новый продукт» (имя + КБЖУ на 100 г)
     -> UserFood с этим barcode
     -> следующий скан находит мгновенно и навсегда, офлайн
     -> (v2.1) «отправить в Open Food Facts», когда появится сеть
```

Каждый промах делает приложение лучше. Это единственный честный способ жить с неполной базой.

### Остальные состояния

| Ситуация | Поведение |
|---|---|
| База ещё качается | Скан и поиск идут по ядру, статус «база: 43%» |
| Парсер не понял сегмент | Не ошибка — поиск с подставленной строкой |
| Несколько кандидатов | Список, первым — самый частый у пользователя |
| Камера запрещена | Ручной ввод цифр штрих-кода |
| Абсурдный КБЖУ | Отсечён на сборке + валидация при ручном вводе |
| Докачка оборвалась | WorkManager возобновляет, sha256 ловит битый файл |

## 9. Тестирование

- **Парсер** (`:core:resolver:impl`) — табличные юнит-тесты, десятки кейсов ru/en,
  включая грязные: `200гр гречки`, `пол-ложки`, `2шт`, `курица 150`. Пишется по TDD.
- **`:core:fooddb`** — фикстура ~1000 строк, проверка ранжирования FTS5.
  Каждый поисковый тест гоняется в **обоих состояниях**: только `seed.db`
  и `seed.db` + приattachенный `food.db`. Это главный источник багов «работает
  до докачки, ломается после».
- **`:core:repositories`** — подстановка нутриентов, корректность снимка в дневнике.
- **`:feature:diary`** — суммы за день, границы суток, смена таймзоны.
- **Скрипт сборки БД** — инварианты на выходе: нет NULL в обязательных полях,
  ккал в диапазоне, нет дублей barcode, FTS покрывает все строки.
- **Compose UI-тест** на экран подтверждения.

## 11. Что в v1 намеренно НЕ входит

- Аккаунты и облачная синхронизация. Данные локальные, есть экспорт/импорт.
- Рецепты и составные блюда. Появятся, когда станет больно.
- Вода, шаги, интеграция с Health Connect.
- Дельта-обновления базы.
- Отправка данных в OFF (нужна сеть, отдельный этап).
